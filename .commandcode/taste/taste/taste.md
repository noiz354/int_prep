- Prefers comprehensive technical explanations (tech stack + features) to be delivered as persistent markdown docs in `docs/`, organized per engineering area (frontend, backend, data analytics, data engineering, ML, AI agent), rather than chat-only summaries. Confidence: 0.7
- Prefers precise, honest progress definitions: explicitly distinguishes "local foundation / provider-ready adapter" (implemented, runnable, testable) from real external vendor/production integration, and refuses to claim production readiness without actual vendor backing, credentials, and org approvals. - Expects progress claims (e.g., "% PRD coverage", "done") to be backed by executable, verifiable automated checks — test suite results, successful build, feature-registry validation, security audit, and skills/scripts validation — rather than asserted. Confidence: 0.9
- Prefers executing work strictly according to phased plan documents with explicit approval gates — one phase at a time, stopping at every gate for approval, never continuing silently (e.g., following a "finish stubs" phased productionization prompt and choosing the mandated starting phase, Phase 0 decision brief, over skipping ahead). Confidence: 0.9
- Produces structured phase reports at each gate in the format the process mandates: status, PRD IDs touched, decisions made, security/privacy/AI impact, test/build/audit results, docs updated, and an explicit approval question. Confidence: 0.9
- Approves gates and proposed next steps with terse, single-word go-aheads (e.g., "lanjut", "iya buatkan...") rather than elaborate confirmations, and expects the assistant to then proceed autonomously through the agreed finalization steps — updating document statuses (DRAFT → APPROVED), appending final results sections, re-running the full verification suite, and delivering the closing summary — without further back-and-forth. Confidence: 0.6
- Prefers settling provider/deployment strategy (decision matrix/brief, no code) before writing implementation code, and explicitly flagging missing credentials/approvals as blockers rather than assuming them. Confidence: 0.8
- Prefers operational artifacts, not just status labels: an unblocking checklist template with per-item owner, concrete steps, and evidence-of-completion columns plus a status tracker, so a capability can be reclassified from "blocked on provider decision" to "production deployed" only when evidence is attached. Confidence: 0.6

Confidence: 0.7
- Prefers honest limitations/caveats of a chosen approach to be persisted as a dedicated, discoverable markdown doc (e.g., `docs/HONEST-LIMITATIONS.md`) capturing what cannot be fully solved, the org decisions still required, and the status-reclassification criteria — not left as chat-only disclaimers. Confidence: 0.8
